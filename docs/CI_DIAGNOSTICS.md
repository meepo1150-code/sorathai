# Sorathai CI diagnostics — M15

This document explains how to investigate repository validation failures without changing production behavior merely to make a gate green.

## Validation pipeline

The `Validate static website` workflow currently runs:

1. static HTML/link/metadata/sitemap validation
2. Node unit/model tests
3. generated reading-content review
4. reproducible npm installation for browser-test tooling
5. Chromium installation
6. Playwright browser regression
7. whitespace validation

A failure should be fixed at the layer that produced evidence. Do not bypass or weaken an assertion simply because a later layer is expensive to rerun.

## Playwright failure evidence

On CI, Playwright is configured to preserve:

- a screenshot only when a test fails
- a trace for failed tests
- an HTML report generated with `open: never`

When the workflow fails, GitHub Actions uploads a short-retention artifact named like:

`playwright-diagnostics-<run-id>`

The artifact may contain:

- `playwright-report/` — HTML report and test summaries
- `test-results/` — per-test failure output, screenshots and trace archives where Playwright produced them

Successful browser runs intentionally do **not** upload these diagnostics. The HTML report may be generated transiently inside the runner, but artifact storage is reserved for failures so routine green runs do not accumulate unnecessary data.

If the workflow failed before Playwright produced files, artifact upload intentionally uses `if-no-files-found: ignore`; absence of a browser artifact is then expected and the earlier failing step is the source of truth.

## Reading a browser failure

Recommended order:

1. read the failed test name and assertion in the Actions log
2. inspect the failure screenshot for visible state
3. open the Playwright trace when the timing/navigation/state transition is unclear
4. compare the failing path with the relevant unit/static contract
5. reproduce locally only if the CI evidence is insufficient

Do not treat screenshots as calculation truth. They are presentation/runtime evidence only.

## CI concurrency

The validation workflow uses a concurrency group based on the workflow plus PR number/ref and cancels superseded runs.

Benefits:

- a newer commit to the same PR does not leave an obsolete expensive Chromium run consuming time
- repeated pushes to the same ref converge on the newest state

Trade-off:

- an older run may show `cancelled` rather than a final pass/fail result. This is intentional when a newer commit supersedes it.

A push to `main` still triggers its own validation run. The production crawler smoke remains a separate workflow and operational signal.

## Dependency reproducibility

`@playwright/test` remains pinned to `1.55.0` in `package.json`. M24 added `package-lock.json` generated by npm 10.9.8 on the repository's GitHub-hosted Node 22 runner and reviewed the resolved graph before committing it.

CI now uses `npm ci --no-audit --no-fund`, so the browser-test npm dependency graph is installed from the committed lockfile rather than re-resolved on every run. Intentional Playwright upgrades must update `package.json` and regenerate/review the lockfile together, then pass the full browser gate.

The lockfile improves npm dependency reproducibility; it does not pin the separate Chromium binary downloaded by Playwright outside npm, nor does it change any production browser dependency.

## Guardrails

CI/diagnostic work must not change:

- astrology calculations or reading outputs
- DOB/profile/navigation behavior
- SEO/canonical/Search Console contracts
- analytics transport/privacy boundary
- visual design solely to satisfy a diagnostic artifact
- monetization/backend/account scope

Fix reproducible defects; do not manufacture green evidence.
